# Tracked prose outside the guard still blocks owners with common surnames

- **Priority**: P1 (this round)
- **Area**: repo
- **Source**: session 2026-08-20, cluster C11 (leak-guard usability, issue #307)
- **Claimed-by**:

## Goal

Get the number of leak-guard violations an owner sees on a clean checkout — caused
purely by this repository's own writing about surnames — down to zero, for every
surname that is not also an ordinary English word.

## Context

Issue #307's boundary fix stopped a surname hiding INSIDE an ordinary word from
firing (`making`, `agreed`, `cross-session`). A second-order version of the same
defect survived it: the repository **writes about** that bug, and to do so it
spells out the very surnames it is describing. Those spellings are bare words in
tracked files, so an owner who shares one is blocked by documentation they never
wrote and cannot interpret without reading the scanner.

The guard's own test module was fixed in the branch `fix/leak-guard-usability`
(commit "stop the guard's own tests blocking common surnames") by assembling
those fixture values from split string literals — the idiom that module already
used for PII fixtures — and pinning it with `ThisModuleIsSurnameCleanTests`,
which re-scans the file with the guard's real matcher. **That fix stopped at the
guard's own files, because the rest is outside those files' ownership.**

Still spelling surnames out, measured on the tracked tree at that commit:

| File | What it is |
|---|---|
| `message-queue/needs-human/decisions/leak-guard-homonym-surname-allowance.md` | the open owner decision; names ten surnames with before/after counts. The single biggest remaining source. A two-way owner document — amend it, never clobber it. |
| `tasks/0_backlog/2026-08-09-issue-triage-2026-08-03-batch/task.md:141` | the triage row for #307, naming three surnames |
| `automation/shared/config.py:649` + its five `_vendor/` copies | the accessor docstring for `leak_guard.english_word_tokens`, naming four. Edit the canonical file and re-run the vendoring sync; never edit a `_vendor/` copy by hand. |
| `config.example.yaml:48` | the commented example for the same key, naming the same four |

Reproduce the current list without spelling anything out here — pick any surname
and run:

```
JOBHUNT_PERSONAL_TOKENS='<surname>' .venv/bin/python automation/publish/check_public.py
```

Exit 1 with a `[6]` section listing only prose files is the defect; exit 0 is
done.

**Two different cases, and they need different answers.**

1. **A surname that is not an ordinary word in this repo's vocabulary.** These
   should reach zero, by rewriting the prose the way the test module was
   rewritten — describe the collision without naming the person. Note that a
   visible in-place marker does NOT work: brackets, case humps and underscores
   all CREATE the word boundary the matcher looks for. Split literals work in
   code; in Markdown, the answer is to not name the surname at all.
2. **A surname that IS an ordinary word** (a colour, a length, a speed, a place
   name). These can never reach zero — the repo legitimately uses those words
   hundreds of times, and no rule can separate a town from a person. That case
   is what the opt-in `leak_guard.english_word_tokens` allowance is for, and as
   of the same branch the guard now names it in its own failure output.

So the target is case 1 only. Case 2 needs no code change; if anything it needs
the handbook paragraph added in that branch to stay accurate.

**Constraint that outranks the goal:** do not weaken detection to reach zero. No
per-file exemption list, no relaxed boundary rule, no dictionary inference (that
last one is Option C in the open decision file above and was argued against
there). The fix is prose, or it is not a fix.

## Definition of done

- [ ] For each surname in case 1, the command above exits 0 on a clean tree.
- [ ] The open decision file is amended in place (dated, appended) rather than
      rewritten, and still explains the trade it exists to ask about.
- [ ] The vendored `config.py` copies are regenerated by the sync script, not
      hand-edited, and the vendor drift gate stays green.
- [ ] No change to `classify_tokens`, the boundary rule, the allowance
      mechanism, or any exit code.
