## Why auto-slug-and-correct was the wrong option, with the measurement

The task itself recorded the suspicion — *"slugification is already lossy and inconsistent in the
live data … the existing folder slug cannot be trusted as the key."* Phase 7 measured it:

- 227 of 243 application folder slugs equal `slugify(company) + "-"`; **16 do not**, and the 16 are
  mutually contradictory. The same trailing category word is dropped in 4 cases and kept in 8. The
  same CamelCase pattern is split once and kept once. Dots become a hyphen twice and vanish once.
  Legal suffixes are dropped 3 times and kept twice.
- So there is no rule to auto-slug *with*. Any rule contradicts the existing data somewhere, and
  "correct incrementally" means discovering that one employer at a time, forever.

## What made one pass affordable

One slug rule replaced every historical one — lowercase, `&`→`and`, each run of non-`[a-z0-9]` to a
single hyphen, **nothing dropped**. Applied to `display` rather than to the folder slug, it
**reproduced all 25 existing `private/companies/` folder names exactly, with zero overrides**. That
is independent evidence the rule matches the judgement the owner was already applying by hand — and
it means no company folder is renamed.

All remaining judgement was pushed into choosing `display`, which is what the 7 questions ask
about. Two strings merge only under a named mechanical rule (normalisation, the public resolver's
own legal-suffix list, one trailing parenthetical, or the registry's curated alias list) — never
fuzzy matching. The evidence-override rule fired **zero** times.
