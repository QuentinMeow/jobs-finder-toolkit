# The orientation skill names an overlay-only skill, which two policy lines say never happens — which side gives?

- **Status**: awaiting-owner-input
- **Filed**: 2026-07-31
- **Source**: [public/private split handbook](../../../docs/handbook/public-private-split.md)
- **Blocks**: nothing. The line has shipped since the skill was written and no gate
  fires on it.
- **Default path**: leave the sentence exactly as it is, and name no *additional*
  overlay-only skill anywhere in the public tree. Agents do not remove it unilaterally
  — it is an instruction-file edit that deletes a real affordance, and deleting an
  affordance is not a mechanical fix.
- **Cost if wrong**: ratify
- **Safe to merge because**: the sentence stays as shipped; changing it is a one-line doc edit and
  the leak guard already passes on it.

## Background

This item is deliberately written without repeating the sentence in question or the name
it contains. Read it at `skills/ask-me-anything/SKILL.md:208-209` — a two-line
parenthetical at the end of the interview-prep section, describing one capability as a
separate private skill that ships only with the overlay.

**The policy it contradicts**, stated twice and both times as an absolute.
`AGENTS.md:40-41`:

> **PRIVATE skills are intentionally not enumerated here**: each entire skill lives only
> in the overlay, and bootstrap discovers it dynamically.

`docs/handbook/public-private-split.md:26-28`:

> **PRIVATE skills** are intentionally **not named in this repository**. Each entire
> skill (SKILL.md + scripts/assets/evals and products) lives only in the private
> overlay and never ships in the public repo.

Everything else about the mechanism works exactly as designed: the skill's directory is
`private/skills/<name>`, the runtime adapters that point at it are generated by
`automation/bootstrap_overlay.py` and their paths live only in repository-local Git
metadata, and nothing tracked in this repo references the directory. **The prose is the
only leak; the plumbing is clean.**

**Why no gate catches it, precisely.** This is more interesting than "no gate looks",
which is what I expected to find and is not what is happening:

- The leak guard *does* tokenize private skill names. `automation/publish/check_public.py:448-464`
  (`_overlay_skill_name_tokens`) walks `private/skills/` and adds every child directory
  that owns a `SKILL.md` to the supplementary token set, specifically so that "adding or
  renaming one arms the local content/path scan for that name automatically, while the
  public copy of this guard never carries the name itself."
- Those tokens are matched as a **case-insensitive substring** of each line
  (`:732`, `:793-795`).
- `automation/hooks/pre-push:136` runs the guard **armed** over the whole tree on every
  push from your machine, where the overlay is mounted. Your tree is green.

Put together, that is a proof: the sentence does not contain the skill's directory-name
token. It names the capability in ordinary English instead. So the guard is armed, it is
looking for this exact class of leak, and this instance slips past it on spelling alone
— a paraphrase away from being caught, in either direction.

**What the sentence buys.** It is the answer to "the toolkit clearly has more skills than
`skills/` lists — where did the others go?", asked by the one skill whose job is
orientation. Delete it and a reader of the public repo learns nothing about why their
runtime shows capabilities the tree does not; a reader of your own checkout is told
nothing about which of their skills will not survive an export.

**Related but separately answerable:** `message-queue/needs-human/decisions/company-detector-over-the-skills-tree.md`
is about the sibling class (a real company name in a public skill file, likewise invisible
to the armed token scan). If you adopt its Option B — a whole-tree advisory scan over
`skills/*/SKILL.md` and `LESSONS.md` — this line is a natural second detector on the same
pass. It does not decide this item either way.

## Options

### Option A — delete the parenthetical

`AGENTS.md:40-41` and `public-private-split.md:26-28` become literally true, and stay
true, with no policy edit.

*Cost:* the orientation gap above, in full. It is a real one — someone whose runtime lists
a capability the public tree never mentions has no way to find out where it comes from,
and the orientation skill is the exact place they would look.

### Option B — keep it, and soften both policy lines

Both become "no private skill is named except in the orientation skill's dependency note".

*Cost:* an absolute with one carve-out is much weaker than an absolute, because the next
editor now has to judge whether their case is like the carve-out. And the carve-out is
exactly where a new-user-facing document is most tempted to add another one.

### Option C — rewrite the sentence to keep the affordance without the name

Something with the shape of: *"Some interview-prep capabilities ship only with the private
overlay and are not part of the public toolkit; when an overlay is mounted, your runtime
lists them alongside these."* No name, both policy lines stay absolute and true, and the
question the parenthetical answers is still answered.

*Cost:* a reader who remembers the capability by name and greps the public tree for it
finds nothing and concludes it does not exist. That is a genuine, if small, regression for
a returning user — and it is the entire cost.

## Recommendation

**Option C.** What a newcomer needs from that parenthetical is "the list you see may be
longer than the public one, and here is why" — the specific name is not carrying the
orientation weight, it is just how the sentence happens to be phrased. C keeps the
affordance, keeps both policy statements absolute, and costs one sentence rewritten.

Option A is the cheapest to execute and defensible if you would rather the public tree
simply say less. Option B is the one I would avoid: it converts two clean invariants into
a rule with an exception, and the exception lives in the document most likely to grow more
of them.

Whichever you pick: it is an edit to a `SKILL.md`, so the risk-based eval gate applies.
A rewrite that changes no routing behaviour (C) is the mechanical case — record the
one-line skip rationale per `evals/README.md` rather than skipping silently.
